# Evaluation protocol

OfacMatch's matching is improved by looking at where it fails. If the same cases are then used to report how well it works, the numbers measure how closely the code was fitted to those cases, not how well it screens names it has not seen. To avoid this, the evaluation uses two separate sets.

## The two sets

| | Development set | Held-out test set |
|---|---|---|
| Purpose | Finding weaknesses and adjusting the method | Reporting results, once |
| Listed parties | 400 individuals and 200 entities, seed 42 | 400 individuals and 200 entities, seed 1042, none of them used in development |
| Nickname cases | 200, drawn from the whole list | 200, from entries not used in development |
| Ordinary names | 2,000 two-part and 1,000 three-part names from the development vocabulary | The same numbers, from a separate vocabulary of 50 first names and 57 surnames never used in development |
| Near-miss names | 1,000, listed first names of the development sample with development surnames | 1,000, listed first names of the test sample with held-out surnames |
| Can be looked at | Freely | Only after the method is frozen |

Both sets contain the same kinds of variation: the original ten (exact, reordered, formatting, single-letter errors, transliteration, joined particles, a dropped middle name, a changed company legal form) and five harder ones (a wrong first letter, two wrong letters, a nickname or the same name in another language, a first name as an initial, and an extra middle name not on the list).

The development set includes every case used in the evaluation of release 0.1.2, unchanged, so earlier results can still be reproduced.

## Rules

1. All changes to the matching method, and all choice of settings such as penalties and weights, are made by looking at the development set only.
2. Before the held-out test, the method is frozen: the code is committed and the commit is recorded below.
3. The held-out test is run once, for OfacMatch and every baseline, with the thresholds and settings fixed beforehand. The harness refuses to run it without `--final`.
4. Its results are reported as they come out, whether OfacMatch does better or worse than the baselines.
5. If the method is changed after the held-out test, the held-out results no longer count as a test of the changed method. A new held-out set (a new seed and a new vocabulary) is needed, and that is reported.

## Settings chosen on the development set

**Extra-part penalty** (`ScoringOptions.ExtraPartPenalty`, how much each letter of a searched part that is not on the listed name costs). The rule below was written down before any candidate was run.

- Candidates: 0.5 (the first value, chosen without measurement), 0.4, 0.3, 0.2, 0.1 and 0.
- Choose the candidate with the highest recall on all development positive cases (original and harder variations) at the threshold where at most 5% of all development ordinary names (two-part and three-part) alert.
- Constraint: recall on the original cases at the threshold where at most 1% of ordinary names alert must not fall by more than 0.5 percentage points compared with 0.5.
- Ties within 0.1 percentage points go to the larger penalty, which is the more cautious choice.
- **Result** ([docs/tuning.md](tuning.md)): 0.1, with 97.3% recall at alerts ≤ 5% (0.5 gave 91.8%) and 95.4% on the original cases at alerts ≤ 1% (0.5 gave 95.3%). The cost: at a fixed threshold of 85, three-part ordinary names alert more often (22.5% against 7.1%), because a listed two-part name inside a longer searched name now scores high. Organizations that screen many three-part names at 85 should expect that.

**Not done, on purpose:** a dictionary of nicknames and equivalent names (Aleksandr and Sasha, Yusuf and Joseph). The nickname test cases are generated from such a dictionary, so adding one to the matcher would only show that the matcher and the test share a list. It needs an independent source and independent test cases.

## Commands

Development set (any time):

```bash
dotnet run -c Release --project eval/OfacMatch.Evaluation -- --data <folder> --out docs/evaluation.md
dotnet run -c Release --project eval/OfacMatch.Evaluation -- --data <folder> --baselines --out docs/baselines.md
```

Size of each set, without scoring anything:

```bash
dotnet run -c Release --project eval/OfacMatch.Evaluation -- --data <folder> --split test --sets-only
```

Held-out test set (once, after freezing):

```bash
dotnet run -c Release --project eval/OfacMatch.Evaluation -- --data <folder> --split test --final --out docs/evaluation-heldout.md
dotnet run -c Release --project eval/OfacMatch.Evaluation -- --data <folder> --split test --final --baselines --out docs/baselines-heldout.md
```

## Limits

Both sets are synthetic: the variations are generated by rules, and the ordinary names are combinations of common names. A held-out set protects against fitting the method to particular cases, but not against the generator itself missing kinds of variation that occur in practice. Real, anonymized screening data would be the stronger test.
